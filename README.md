# AEO-Engine

The fortnightly answer-engine research machine for Krish Raja's ventures, the companies he wants to sell to, and the companies he wants to be like. Every other Sunday it asks the AI assistants (Perplexity, ChatGPT, Claude, and Grok when a key exists) the questions those buyers ask, records who gets cited and whether we do, scores the demand behind each question, and ships one packet per subject to Control Center, which turns the recommendations into content ideas and the probes into the Growth tab's evidence. It keeps no list of its own: every subject, domain and competitor comes from Control Center, so adding a company there is the whole onboarding.

## Never publish

A writer working from this repo's exhaust may not reveal:

- any credential or secret VALUE, and no secret NAME outside this README's secrets table
- any call participant's name, email address or handle, or any transcript text
- any theme paraphrase or call reference from a packet
- any prospect company name, room target, title, or trigger signal
- any engine answer snapshot or citation list
- any figure from a cost ledger or a packet's stats
- any win kit (it goes to Control Center only), or any URL or text of a page the site reader fetched

The full list with reasons is `docs/NEVER-PUBLISH.md`.

## How it runs

`.github/workflows/aeo-weekly.yml` (named AEO weekly) is scheduled for Sunday 04:00 UTC on odd ISO weeks only (fortnightly since 2026-10-15; the file keeps its name so Control Center's links hold). GitHub starts scheduled runs late: every scheduled research run from 2026-09-27 to 2026-11-08 began between 08:50 and 10:56 UTC. It also runs on a manual dispatch, Run workflow in GitHub Actions (subject, dry; a dry run on Actions prints counts only and keeps no file, because this repository's artifacts are public, so read a whole packet with `--dry --out` locally), which is how Krish starts a run by hand today, and on `repository_dispatch` type `aeo-run` from Control Center's Run now route (`/api/aeo/run`, served by content-engine; `client_payload.command_id`, `client_payload.subject`). No Control Center page presses that route any more, and no `aeo-run` dispatch has reached this repository since 2026-09-08. Each subject job tries twice, five minutes apart; the second failure fails the job so GitHub notifies. `week_start` is the Monday that owns the run in UTC, so the Sunday run reports the week that began the previous Monday.

Locally:

```
npm install
npm run run -- --subject all --dry --out out/packets.json     # live reads, no POST
npm run run -- --offline --dry --subject ctrl                  # fixtures only, no network
npm run run -- --subject mindmake --rehearse --cap-usd 3        # live probes, packet validated by production, nothing written
npm run rehearse                                               # free: context features and fixture packets against production
npm run run -- --subject <slug|uuid|all> [--week YYYY-MM-DD] [--command-id n] [--cap-usd n]
npm test && npm run typecheck && npm run check:config
```

The research workflow's off-week Sunday runs a verify run only on Krish's approved go-live (below, "The verify lane"); otherwise it is skipped, as before.

The pipeline per subject (`src/pipeline/`): `00-context` reads Control Center and applies Krish's ruled domain corrections (`config/own-domains.json`); `10-transcripts` lists the last fourteen days of Fireflies calls, attributes each to one subject with one model call, and writes five to ten themes with paraphrase-only evidence (Fireflies is a retired route since 2026-11-13: the research workflow passes no key, so this stage reads no calls and every packet says `fireflies_unavailable`); `20-gap` tallies who is cited where we are absent; `30-propose` asks for 25 to 40 questions and carries last week's ids, with a venture engine's requested questions first; `15-site` audits our own hosts with the site reader (below) while the probes run, or, in the research workflow, takes them from the run's site job, which reads each host once for every subject; `40-probe` asks every engine, requested questions first, up to the per-subject limit (25 since 2026-11-13, raised to hold every requested question plus five, never above 30) and the USD cap, and measures each answer's first citation before the packet's cleaning, in the order `55-panel` sets (a venture's requests, its shipped questions, the kits in flight, last run's wins, last run's cited questions, then the rest); `41-samples` asks each contested question twice more on every engine that answered it, at most eight a subject, so one noisy answer is never read as a win; `45-pages` finds our best page for each question and reads the pages cited first; `52-diagnose` gives each question its gap class, why it is not won; `50-score` scores demand out of 100 from three measured proxies and ranks the recommendations by kit priority; `60-digest` writes the recommendations, watch list and (per kind) the approach hook or the playbook, with a deterministic fallback; `65-voice` rewords those drafted lines in Krish's approved voice rules, only when the directive carries at least one, and never decides or scores anything; `62-kits` prepares a win kit for each of a venture's questions that is not won; `55-panel` then gives each asked question its state and its history in research weeks (`docs/PACKET.md`, "Gated fields"); `68-features` attaches the optional packet fields Control Center lists in `packet_features`, and only those; `70-ship` validates and POSTs. A stage added for the diagnosis that fails degrades to its fallback and never fails the subject (`src/pipeline/stage.ts`). Every client has an offline twin that reads `tests/fixtures`, so the same pipeline runs with no network. A prospect's questions are what that company's leaders would ask an assistant about their own problem; the read is whether Mindmake or Krish appears in the answer they would see.

## The rehearsal

Production's ingest (content-engine `api/aeo/ingest.ts`) validates the whole packet before it reads the subject: a field it refuses is a 400 with the errors, and a valid packet whose subject id is unknown is a 404 `unknown_subject` with no row written. The rehearsal (`src/lib/rehearse.ts`) sends a copy of a packet under a fixed synthetic subject id that is never a subject's, so 404 `unknown_subject` means every field was accepted. The only trace is one `aeo_ingest` row in content_engine_runs per packet, recorded as failed with `unknown_subject`.

- **Free:** Run workflow on AEO rehearsal (`aeo-rehearsal.yml`, no paid key): it checks that production's context lists every packet feature this engine sends plus `meter_billing`, and sends the full-feature and v1 fixture packets.
- **Paid, on Krish's yes only:** Run workflow on AEO weekly with one subject, dry ticked and `cap_usd` (at most `AEO_MAX_USD_PER_RUN`; 3 is enough for one subject). The probes run live inside that cap (the Claude Code lane, forced ChatGPT search, the meter's billing rows), and the subject's real packet goes to production's ingest under the synthetic id. A dry run also sends no protocol report and patches no command.

The protocol is [Control Center's ENGINE-PROTOCOL.md](https://github.com/krishanraja/control-center/blob/main/docs/app/growth/ENGINE-PROTOCOL.md), which is authoritative; `docs/control-center/ENGINE-PROTOCOL.md` is a copy of it, taken whole on 2026-11-12, that lags it from its next change. Each report sends the lowest version that carries the fields it uses (`versionFor` in `src/protocol/reports.ts`): 1.0.0; 1.1.0 when a proposal carries a `stage` and `parent_proposal_id` (a kit plan or a check-in, below); 1.20.0 when the directive serves the engine's state; 1.22.0 when a research report says which venture requests it asked. It accepts any 1.x directive, and its decisions are read loosely with 1.1.0's stage and Krish's amended version and 1.6.0's `carried_out` and `reason_code` (`parseDecision` in `src/schema/report.ts`). Since 2026-11-12 it is the one AI-answers specialist every venture's growth engine calls (Ruling, Krish, 2026-11-12; registry `role: specialist`), not Mindmake's engine; Control Center shows it once, under OS, and each venture's own AI-answer standing on that venture's engine tile. The client is `src/clients/growthEngine.ts` (HTTPS only, no redirects, twenty seconds a call, the bearer in one header and never logged); the reports are built in `src/protocol/reports.ts`, sealed with a SHA-256 digest of their canonical JSON (`src/lib/canonical.ts`), and driven by `src/protocol/loop.ts` through `npm run protocol`.

On a research Sunday the wake comes after the 04:00 slot but before GitHub starts the run, so until that run has reported, the run to come is today's. Then the readback, his decisions and the terminal attempt. This workflow holds no paid API key and never calls the research CLI, and `check:config` fails if it ever does: a directive cannot start paid research.

The report carries `queries_cited_first`, one plain line per subject (ventures by name, prospects and aspirations by number only), a line with the questions a majority of the assistants cited first beside it and the panel's states, a `wall: spend` proposal only when the cap stopped probes, at most one win kit plan behind `strategy`, at most three check-ins on the plans Krish approved, and its events (below).

His instruction (`krish_instruction`) is kept by id only; the client drops his words, because this repository and its Actions logs are public. Only paid research can act on it, and the daily run never starts paid research, so the daily run puts it first and acks it `received`, then `blocked` with a line that says when research will reach it: the next scheduled run, when that comes more than 12 hours before the instruction lapses, or else the date it lapses and the press that starts a run by hand (Run workflow on AEO weekly in GitHub Actions). Control Center carries an instruction for 7 days and the research runs fortnightly, so one given in an off week lapses before the next scheduled run unless Krish starts a run by hand. A research run with it open acks `started` (or `blocked` if the research failed, with the same when) and never `done`, which is his to say. The acks go once; later daily runs only say it is still open. An instruction never authorises a send, post or spend, and never starts paid research. Each daily wake's `run_id` ends in the workflow run and attempt, so a second wake the same day is not refused as a conflict.

Each research job reads them with the directive (`readDirectiveInputs` in `src/index.ts`, never fatal), and a venture subject asks its own product's questions word for word, first, as seeds (`requestsFor`, stage 30), so neither the model nor the question caps drop one. The packet takes each venture's product (`heartside`, `legibility` and `publication` beside the five before); Control Center makes a product's subject from its engine's first request.

The North Star share Krish reads is not this count: Control Center computes it from the packets' probes against its own lists, so the two agree only when its reader applies the same rules (`docs/CONTROL-CENTER-BRIEF.md`, "The first citation: what Control Center's reader must match").

A question the packet lists as not worth chasing gets no kit. A venture's top kit, and the next two, travel in its sealed summary, and the research report carries at most one proposal: the highest-priority kit across ventures that are not held, `aeo:kit:<product>:<first 8 of query_id>`, a plan (`stage: plan`, protocol 1.1.0), prepared, behind `strategy` (AEO never publishes, so it is never a post and AEO never proposes its go-live), on `queries_cited_first`, closed by `kit_won` (referring to the page it changes, the host a new page goes on, or the kit's own id when it is off site), expiring at the next scheduled research run. A page a venture names for the question (a request's `targets` with `features.answer_requests_v2`) becomes the kit's target when it is on one of our domains. Before it picks, the report job reads his decisions of the last 60 days: a kit he declined, or approved and is shipping, is passed over for the next one, never asked again; if they cannot be read, no kit is proposed that run. One kit waits at a time: only a full run proposes one (a run of one subject never does), and a full run started by hand while the last full run's kit still waits renews that same kit, or carries it as it is, rather than add a second. Legibility and Full Time are held (`config/subjects.json`; Control Center's `subject.engine_held` wins when it serves one): measured, with no kit or proposal (Ruling, Krish, 2026-11-13).

## The verify lane

A venture that ships a page waits two to four weeks for one noisy reading. The verify lane (`src/protocol/verify.ts`; brief section I; GET-GOING Steps 1 and 9) re-checks only the shipped questions in the off week. Krish ruled on 15 October that research runs fortnightly, on cost, and a verify run changes that ruling, so it runs only on his approved decision, through the Autonomy steps in AGENTS.md:

1. **The plan.** The daily report proposes the standing plan `aeo:verify-plan:v1` (`stage: plan`, behind `strategy`, its cap of 3 USD as `amount_usd` so he can change it) once the last full research run tracked a question as shipped or a kit in flight, or he approved a kit plan. Its words: "In the off week, re-ask only the questions a venture has declared shipped (or a kit Krish approved), three samples on every engine, at most 10 questions and at most 3 dollars a run. Results never count in the North Star share." His No stops it for good; his decisions on it are read back to 13 November, so no window forgets one. His change to it is taken only when it changes the amount: any other change to its words holds the plan (`verify_plan_amended_words`), never guessed at, with no go-live and no run until he approves it as proposed or with only its amount changed.
2. **The go-live.** With the plan approved, the daily report on the Thursday to Saturday before an even-week Sunday proposes `aeo:verify:<that Sunday>` (`stage: go_live`, `parent_proposal_id` the plan, behind `spend`): `exact_payload` is canonical JSON of `{amount_usd, date, query_ids, samples}`, the query ids sorted, the questions the last full research report names in its verify line (`Questions a verify run would re-ask in the off week`; not won first, shipped before a kit, at most 10), and the amount the price table's estimate rounded up to whole dollars (three samples on perplexity, chatgpt and claude, each at its paid API price: the daily report cannot see whether the verify job holds the Claude Code token, and without it the Claude probes fall back to the paid API), at most the plan's cap (his amended amount when he changed it). The same inputs give the same words all three days, so it waits as one ask.
3. **Live.** The research workflow's off-week Sunday no longer just skips. Its plan job runs `npm run verify -- decide` (`src/protocol/verify-cli.ts`, free GETs with the protocol bearer the research job already holds): it rebuilds the payload it would run from the same research report and proceeds only when the plan is approved, his latest decision on that Sunday's go-live approves it, its `payload_sha256` matches, and no verify report for that Sunday is stored yet (once). Amended, it runs his version when its `amended_sha256` checks out and it reads as a payload for that day. Anything else skips with a reason code and counts in the log. The payload goes to `out/` on the runner and to the jobs as an output, never as an artifact. Because GitHub's "Re-run failed jobs" reuses those outputs, the verify job checks once again itself before it asks anything (`verifyGuard`, `src/index.ts`): it refuses a re-run (`GITHUB_RUN_ATTEMPT` past 1), a payload for another day than today (UTC), and a day whose verify report Control Center already stores, read back first with the protocol bearer; a read that fails refuses too.
4. **The run** (`--mode verify --verify-payload <file>`, `src/pipeline/verify.ts`): each question goes to exactly one subject that holds it in its last research packet (ventures first, then by slug), so only those subjects run and their shares never add up past the amount; each question's words from `subject.prior.queries` by `query_id` (one not found is skipped and counted); three samples on every packet engine and never a gated one (Gemini is not asked), charged inside the subject's share of the amount; no model call, no site read, no brand check or sheet, and one attempt (a verify spend is never retried blindly). A packet goes to Control Center only when its context lists `run_kind`, as `run_kind: verify`; otherwise the results go only into the report.
5. **The report** (`aeo:<date>:verify`): the closing event `verify_ran` on the go-live, with the workflow run as its evidence; `question_won` and `question_lost` against the last research panel; one line of counts (questions asked of the payload's, samples, engines); no objective, because `queries_cited_first` stays the research run's.
6. **The check-in.** While the plan is open, the daily report checks in on it (`aeo:verify-checkin:v1`, `stage: check_in`, naming the plan, behind `strategy`) after an off-week Sunday that ran or was skipped, and at least weekly. Its words cover each off-week Sunday since he approved it (in the last four weeks): ran, with the questions asked, the samples and the panel moves; skipped, with its reason; or why it did not run; and the totals. Counts only, never a question, an answer or a URL. His yes keeps it going; his No stops the plan for good. The daily report reads back the verify reports it needs (free GETs, at most two).
7. **A go-live that did not run.** After an off-week Sunday whose go-live he approved, when no verify report for it is stored, the daily report says so in a line and a hold. The hold's reason is the one the plan job's records give (his decisions as they stood that Sunday and the research report it read, rebuilt the way it rebuilt them), or `unknown` when they say it should have run or a research run reported since. The plan job posts nothing itself.

An approved plan never goes live by itself, and nothing here sends or posts; the only spend is the verify run, on his yes. `tests/verify.test.ts` proves it against the stand-in.

## The site reader

How this engine reads a web page, and the only way it does (`src/clients/site.ts`). During research for the diagnosis a headless browser render of the venture sites fired their tracking pixels; so:

- **Fetch only.** GET only, and never a script run: no browser, no DOM, no JavaScript. `check:config` refuses a browser automation package (playwright, puppeteer, jsdom and the like) in `package.json`.
- **Redirects by hand.** `redirect: 'manual'`; at most three hops, each on the registrable domain the request started on.
- **Text only.** HTML, XML, plain text, Markdown and JSON. A path naming a script, a stylesheet, an image, a font or a file is never requested; a response of another type is refused unread. The body is cut at 512 KB; the deadline is 15 seconds.
- **Per host:** at most 40 requests in a process, at least one second apart, each counted; a host that fails three times in a row is read no further. Each request's slot (its count and its start time) is reserved before it waits, so calls made at once to one host still go a second apart and never past the budget.
- **Our hosts once a run.** Many subjects share a host (every prospect's "ours" is Mindmake's and Krish's sites), and each subject runs in its own job, four at a time, so the research workflow's site job reads every subject's own hosts once, in one process, before the subject jobs start (`npm run site`, `src/site.ts`), and seals the result to the workflow run. A subject job reads its hosts from that file (`--site-in`) and never requests one of our pages; if the site job failed, the run has no audit rather than a second read. In a local run, one process, each host is read once and shared by the subjects that name it.
- **Public hosts only.** Never an IP literal, localhost, a single-label name or a private zone (`.local`, `.internal`, `.lan`, `.home.arpa`), and never a port but the scheme's own, on the first request or any redirect hop: a page cited first is a URL an engine gave.
- **A retry reads nothing.** The research job's second attempt is a fresh process with a fresh count, so it reads no page cited first (its own hosts still come from the site job's file).
- **An honest User-Agent:** `AEO-Engine/1.0 (+https://github.com/krishanraja/AEO-Engine; fetch-only audit)`. It never poses as a crawler: robots.txt is read as itself and resolved for each bot's token (OAI-SearchBot, ChatGPT-User, Claude-SearchBot, Claude-User, PerplexityBot, Perplexity-User, Googlebot, Bingbot, Applebot). The audit asks robots.txt, as its own token (which falls to the `*` group), before every read past it, the home page and each sitemap included: a path it closes is not read, and a gate it therefore could not measure is left out, never failed. A robots.txt that answers 4xx means there is none, so everything is open; one that cannot be read (a 5xx, or no answer) closes the host, as RFC 9309 says, and nothing past it is read.
- **Our own hosts** (`src/pipeline/15-site.ts`): at most three a subject, from the domains the probes read (a general platform is never audited as ours, and a domain with a path counts only when its registrable domain is also one of the subject's plain domains, so a profile on github.com or substack.com never puts that platform in the audit); robots.txt, the sitemap inventory (two index levels, 200 URLs a host), the home page and up to 25 pages a host, answer-like paths first, of which a subject's diagnosis reads up to 25. Pass or fail gates a host, never a score: search bots allowed, user bots allowed, home page 200, home page served with 150 words or more, one H1, a sitemap.
- **Pages cited first** (`src/pipeline/45-pages.ts`): at most 15 a subject and 3 a host, fewer a host when a run has more than 13 subjects so no host gets more than 40 reads from one run, the highest-priority questions first; never their links; a video or a forum thread is typed and not read. The one-second spacing holds within a subject job; jobs run four at a time, so two of them may read the same third-party host in the same second. A first citation whose URL carries an email or a handle is still the first: its host is kept and it is never read.
- **Logs carry counts only**, never a URL of a third-party page or a page's text. Packets are unchanged. Tests use a fake fetch and the synthetic pages under `tests/fixtures/site/` (`OfflineSite`); no test touches the network.

## The engines and the Claude lane

Perplexity (sonar), ChatGPT (`gpt-5`, Responses API with web search) and Claude are always asked; Grok joins with `XAI_API_KEY`, and Gemini (`gemini-3.6-flash` with Google Search grounding) with `GEMINI_API_KEY`. Gemini is gated: `gemini` is not in the packet's engine enum, which is joint with Control Center and closed, so its answers are counted only in the sealed summary, beside the packets and never toward `queries_cited_first`, until Control Center's context lists `packet_features: ["engine_gemini"]` and Krish has ruled it into the share, set as the repository variable `AEO_GEMINI_COUNTS=true` (`docs/PACKET.md`, "Gemini, the gated engine"). Production has listed `engine_gemini` since 13 November, so the variable is what holds Gemini out; a key added alone never moves the North Star.

Claude probes run on the Claude Code subscription (Ruling, Krish, 2026-11-13), with the paid API as a switch. `AEO_CLAUDE_LANE`, a repository variable read when a run starts, says which:

| Value | What the Claude probes do |
|---|---|
| `code` | One fresh headless Claude Code session per question (`src/clients/claudeCode.ts`): a neutral system prompt that names no venture, WebSearch the only tool, no MCP server, an empty working directory and HOME, and a child environment built from an allowlist that never carries an API key. Its first event is checked and the probe fails closed on any other tool, any API key source but `none` (the value a subscription token alone reports; a missing one is refused too) or a connected MCP server. No paid fallback: a subscription limit stops the lane's later probes. |
| `api` | The Messages API with its hosted web search, at most two searches a probe (`src/clients/anthropic.ts`). |
| `compare` | The code lane for every question, with the API behind it for a probe the subscription's limit stopped (as in `code_then_api`), and the API lane beside it on each subject's first five questions; the two are tallied in the sealed summary (search share, inline citations, first-host agreement, the overlap of the hosts their searches returned) and the API answers never enter a packet. The default for the run of 22 November (a week starting on or before 16 November), so the lanes are read against each other before the API is switched off. |
| `code_then_api` | The code lane, and the API only for a probe the subscription's limit stopped, charged inside the cap. The default from the research week of 23 November, so the shared subscription's limit never drops Claude out of a fortnight's reading. |

Empty or unknown means the dated default. Without `CLAUDE_CODE_OAUTH_TOKEN` every lane falls back to `api`, with one log line, so a missing secret never zeroes Claude. The CLI is installed pinned in the research job (`@anthropic-ai/claude-code@2.1.323`); a new version changes the measurement and is bumped with the tests.

Costs, in words: every paid call is charged against an estimate before it is made (`src/lib/cost.ts`); the run stops probing at the cap (`AEO_MAX_USD_PER_RUN`, default 25) and counts what it skipped, and AEO stays inside its cap of 25 dollars a fortnight. A Claude Code probe costs no API dollar: the ledger counts it at a price of zero and never stops it at the cap, and its tokens are counted against the subscription in the log and the sealed summary and, once Control Center's meter reads billing rows (`meter_billing`), posted as subscription tokens with no dollar amount, never as an API row. A subscription limit (a rate limit status of `rejected`, or paid overage in use) stops that lane's probes (counted, and handed to the API in `code_then_api` and `compare`, inside the cap); past a warning threshold the subscription still serves, so those probes finish and are only counted. Gemini stays in its free tier: a research job stops asking it before 150 grounding queries, a retry asks it nothing, and a skipped Gemini ask is never charged. `compare` pays the API for five questions a subject. The dry run prints the ledger. The meter's billing rows carry each provider's search calls billed per call beside the tokens (`providerSearchCalls` in `src/lib/usage.ts`): OpenAI's `web_search_call` items, xAI's sources used and Gemini's grounding queries; Perplexity's request fee is already priced per call by the meter, so it is not counted twice. Control Center's meter prices them once it holds a rate.

## The packet

`docs/packet.schema.json` is AeoPacket v1, the JSON this engine POSTs to `POST /api/aeo/ingest`. `src/schema/packet.ts` mirrors it in TypeScript with a hand-written validator that refuses any string carrying an email address, an @handle or an em dash. `docs/PACKET.md` explains every field and what it is for. Control Center holds an identical copy of the schema; change it here first and say why.
