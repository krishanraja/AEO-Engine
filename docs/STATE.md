## Changed on 2026-11-13, unproven until the run of 22 November

Live data read on 13 November showed three measurement defects and one serving defect. This change fixes them in code, proven offline by the tests named; nothing here has run live, and the first research run that carries it is the scheduled one on Sunday 22 November 2026. The packet's shape is unchanged (its schema is shared with Control Center and closed); only what `probes[].citations` and `we_cited` mean changed, as `docs/PACKET.md` now says.

Its citations are the `url_citation` annotations in the order they sit in the text. Every probe now searches, so its deadline is four minutes, as Claude's is, not the 120 seconds that already timed some ChatGPT probes out on 8 November; and its spend cap estimate is 0.05 (was 0.03), because every probe now pays for a search and reads its content, and nothing meters OpenAI usage yet. ## Known limits

- The demand score has no prompt-volume corpus behind it; every row's labels say so. Google volume enters only through Control Center's striking-distance rows.
- Recommendations for an aspiration mean "questions where the aspiration is absent"; the useful output for that kind is the playbook. An aspiration is not diagnosed and gets no kit.
- The page match line (0.35 of a question's distinctive words in a page's title and H1, and at least two of them) is a starting value. The distinctive-word rule took out the matches on a shared word, but a page on the same subject still matches a narrower question on it. Read the matches after the 22 November run before trusting an `update_page` target.
- A third-party host gets at most 3 page reads a subject (fewer when a run has more than 13 subjects, so no host gets more than 40 from one run). The one-second spacing holds within a subject job; jobs run four at a time, so two may read one third-party host in the same second.
- A declined kit stays off his list for 60 days (the decisions window); after that its question may be proposed again if it still leads. An approved plan is checked in on for 42 days (`PLAN_OPEN_DAYS`); after that it is neither checked in on nor in flight unless he approves it again. Withdrawing a kit or a check-in (`withdrawn[]`, protocol 1.10.0) is not built: one leaves his list when he decides it or it expires at the next scheduled research run, and with `aeo_kits_delivered` an undecided kit plan is simply no longer carried.
- The registrable domain behind the same-domain redirect rule is the last two labels, or three under a short list of two-label suffixes (`registrableDomain` in `src/clients/site.ts`), not a public suffix list.
- A question's page cited first is the first engine's first inline citation that is not ours; the kit's pages to beat are each engine's first. A gzipped sitemap is not read (its type is not text).
- A held venture is measured and named in the report with its gap counts; only its kit and proposal are withheld.
- The protocol documents no guard on a `strategy` proposal's words, beyond the validator's (no email address, no em dash, 8000 characters). A kit that would fail the validator is held back with `kit_not_proposed` and the report still lands; a kit naming a URL with a long run of digits is sent as it is, and whether Control Center accepts that is first seen on 22 November.
- `probes_skipped_cap` counts pairs skipped by the USD cap only. Queries beyond the per-subject probe limit (25, or the requested questions plus five, never above 30) simply carry no probes. A venture asking more than 30 questions of one subject in one run would have the rest unasked, and its request unserved until a later run asks them.
- Search behaviour (whether an engine searched, its queries, what it retrieved) reaches Control Center only once it lists the `probe_detail` packet feature; until then it is kept for counts only, and Control Center sees only the cleaned inline citations and `we_cited`.
- `queries_cited_first` uses "at least one assistant's first citation is ours", on the first sample, as its rule. That rule is the engine's reading of the objective, not a ruling. Since 2026-11-13 the research report also gives the majority-of-assistants count beside it, as the brief asks, so Krish can decide how the share should read; changing the objective is a one-line change in `src/protocol/measure.ts`.
- The panel's history is only as long as what Control Center serves back. Until it serves `subject.prior.queries[].panel`, a question carried from last week has no known history, and `question_won` and `question_lost` come only from questions first asked this run.
- A kit plan's gap class at approval is read from this engine's own words: the kit as proposed in the last research report, else the last check-in's line, else his amended version. A plan approved from a report older than the last one, with no check-in yet, says "not known".
- Repeat samples re-ask only engines that answered the first pass, and only the packet's engines (never a gated one). A question past the 8-sample cap is judged on its one sample.
- A second full research run on the same UTC day gets a 409 on its protocol report, because one full run a day has one `run_id`. The attempt fails with `report_conflict`; the packets still land.
- An instruction from Krish lapses 7 days after he gives it, and the research runs fortnightly. The daily run never starts paid research, so an instruction given in an off week is acted on only if he starts a run by hand before it lapses; the daily run's `blocked` ack says so, with the dates.
- The calls window is the last fourteen days, the fortnight between scheduled runs. A run started by hand between them reads calls the next scheduled run reads again; a scheduled run that GitHub starts earlier than the last one leaves a gap of at most those hours.
- A verify go-live names only the questions the last full research run tracked (shipped, or a kit in flight). A kit plan he approves after that run reaches a verify go-live only after the next research run tracks it. A full research run started by hand between the go-live and its Sunday changes the questions the plan job rebuilds, so the digest no longer matches and the verify run is skipped (`sha_mismatch`), by design.
- A verify run's panel moves are against the last research panel Control Center serves, which a verify packet does not replace; a win it reports is reported again by the next research run if it holds.
- "Once" for a verify run is checked twice. The plan job runs it only when no verify report for that Sunday is stored. GitHub's "Re-run failed jobs" reuses the plan job's outputs and runs only the failed jobs, so the verify job checks again before it asks anything (`verifyGuard` in `src/index.ts`): it refuses when `GITHUB_RUN_ATTEMPT` is set to anything but 1 (any re-run of the workflow), when the payload's date is not today in UTC, and, with the protocol bearer in its environment (the research job holds it), when Control Center already stores a verify report for that date, read back first; a read that fails refuses too. A refusal exits 1 with a reason code, spends nothing and leaves no summary, so the report job counts the subjects as failed. Its cost, by design: a verify job that failed after it spent is never tried again, since any later try is a re-run; and one GitHub starts after midnight UTC, past its Sunday, is refused as `not_today`.
- Outcomes join pages by normalised URL and a Search Console row by its last day; a row that runs across the shipping day counts in neither window, and the window before shipping is unknown unless a row on the page's host starts on or before its first day. The window ending on the run's day can still hold days before a recent shipping day: it is the last 28 days, read against the 28 before shipping. A landing page given as a bare path is matched only to pages on the venture's own hosts, counted once in its total.
- The cited-pages mention check reads a page's visible HTML as served: a mention a script writes is not seen, and a page closed to this reader by robots.txt stays `unchecked`. The pages-cited-first read now asks robots.txt before every third-party page, and again for a same-domain redirect hop, as the mention check does, so a page the mention check reuses was never read past robots.txt. Each subject's third-party reads on one host (its robots.txt, the pages cited first and the mention check's fresh fetches) come out of an equal share of the host's 40 requests over the run's subjects (`hostShare` in `src/pipeline/45-pages.ts`), so the run's subject jobs together stay inside it; a redirect hop is a request of its own and is not in that count, and with more than 20 subjects the floor of one page a host can pass it.
